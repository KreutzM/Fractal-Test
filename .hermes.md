# Hermes repository policy

This file is the canonical operational policy for Hermes in this repository.
`AGENTS.md` remains binding, `docs/AGENT_OPERATING_MODEL.md` explains the
end-to-end lifecycle, and `docs/AGENT_GIT_WORKFLOW.md` owns Git transport and
publication details.

## 1. Source of truth

Current truth comes, in order of relevance, from:

1. the current Git repository;
2. GitHub issues;
3. the current feature branch;
4. the associated pull request and its discussion;
5. durable repository documentation.

Historical session or chat context must never override current repository or
GitHub evidence. Re-read repository and GitHub state whenever a fact may have
changed. No important requirement, architectural decision, blocker, validation
result, open item, or follow-up may exist only in chat history.

## 2. Issue-first work

Substantive work requires a GitHub issue. Before changing the repository:

- read `AGENTS.md` and this file;
- read relevant architecture and workflow documentation;
- read the complete issue and all comments;
- search for an existing branch and pull request and continue them if present.

One issue normally produces one reviewable pull request. Large work may use a
tracking issue with independently reviewable child or follow-up issues. Do not
silently expand scope when relevant new work is discovered: create an issue or
update the existing tracker, then reference it from the current pull request.
Small fixes immediately required by the current issue contract may remain in
scope.

## 3. Git autonomy

Within this repository, Hermes is expressly authorized to run normal Git
operations autonomously, including:

- `git fetch` and `git pull --ff-only`;
- `git status`, `git diff`, and `git log`;
- `git switch`, `git branch`, and `git worktree`;
- `git add`, `git commit`, `git push`, and `git push -u origin HEAD`.

Use normal Git workflows instead of leaving intended work as loose working-tree
changes. Name feature branches `agent/<issue-number>-<short-description>` and
include the issue number in commit messages when practical, for example:

```text
Improve installation diagnostics (#1)
```

## 4. Git safety

Without explicit user authorization, Hermes must not:

- commit directly to `main` or merge into `main`;
- force-push or rewrite history;
- run a reset or checkout that destroys another person's changes;
- delete another person's branches;
- stash, drop, reset, or discard unrelated user work.

When the working tree contains unrelated user changes, preserve them and use a
separate worktree if necessary. When `main` or another branch changes
concurrently, re-read the remote state first. A private agent feature branch may
be synchronized with current `main` using a normal safe update when no other work
is overwritten. Stop rather than guess at a genuine semantic conflict.

## 5. GitHub autonomy

When `gh` is installed and authenticated, Hermes may autonomously use:

- `gh issue view`, `gh issue list`, `gh issue create`, and `gh issue comment`;
- `gh pr view`, `gh pr list`, `gh pr create`, `gh pr edit`, and `gh pr comment`;
- relevant read-only CI and status commands.

Track new substantive work as issues; use a tracking issue with suitable child or
follow-up issues for large features. Before ending work, push the branch, create
or update its pull request, and make the issue/PR state sufficient for a fresh
chat to continue.

If `gh` is unavailable or unauthenticated, do not install it and do not alter host
credentials. Commit and push the branch normally, then document the exact GitHub
issue or pull-request action that remains.

## 6. Pull-request lifecycle

Use a draft pull request for unfinished work. A fully implemented change that has
received all meaningful local validation may be ready for review. The pull-request
description must contain:

```markdown
## Summary

## Issue

## Design / Decisions

## Validation

## Remaining / Follow-ups

## Handoff
```

Record what changed, the issue being addressed, relevant decisions, and only the
checks actually run. Explicitly distinguish local tests, GitHub CI, CUDA simulator,
physical GPU tests, and manual GUI/smoke tests. Never describe an unexecuted check
as passing. Record remaining work and the current branch/commit plus the next step
for a new agent. Use `Closes #N` only when the pull request fully completes issue
`#N`. Hermes must not merge the pull request without explicit user authorization.

## 7. Session handoff

Before ending substantive work:

1. inspect `git status`;
2. commit intended changes;
3. push the feature branch;
4. update the issue and pull request;
5. record all remaining work explicitly.

Do not create per-session chat handoff files such as `CURRENT-chat-123.md`.
Durable technical knowledge belongs in code, tests, architecture documentation,
`CHANGELOG.md`, `README.md`, or `TEST_REPORT.md`, as semantically appropriate.
Task-specific current status belongs in the issue, pull request, and commit
history.

## 8. Fresh-chat restart

Use this standard restart instruction:

> Work on issue #N. Treat repository and GitHub state as source of truth. Read
> AGENTS.md, .hermes.md, relevant docs, the issue, existing branch/PR/comments,
> then continue from the current repository state.

Hermes must then update `origin`, read the issue, find any existing pull request,
identify the branch, and understand the existing diff and validation before doing
new work.

## 9. Environment autonomy

Hermes may create a repository-local `.venv`, install project dependencies into
that environment, use project test tools, and run existing repository scripts.
Without explicit authorization, it must not use `sudo`, install global Python,
Node, or system packages, alter drivers or the system CUDA installation, change
credentials or SSH keys, or modify unrelated host services.

## 10. Quality

`AGENTS.md` is binding. Run checks relevant to the changed area, including full
regression checks for substantive product-code changes, and add tests for behavior
changes. Always inspect scope and diff, run `git diff --check`, and leave no hidden
debug artifacts. Preserve all numerical and CUDA invariants in `AGENTS.md` and
`docs/ARCHITECTURE.md`; CUDA simulator or CI results are not evidence of physical
GPU performance or driver compatibility. Record required hardware testing as
separately pending when it was not run.

## 11. Documentation ownership

- Update `CHANGELOG.md` for user-visible behavior.
- Update `README.md` only for a material user-workflow change.
- Update `docs/ARCHITECTURE.md` for durable component, data-flow, or ownership
  boundaries.
- Update `TEST_REPORT.md` only for durable validation results or strategy.

Keep documentation changes proportional and avoid mechanical large-scale rewrites.
Provider and model selection belongs to the invocation, not this policy; do not
encode a model identifier as a repository architecture assumption.

## 12. Autonomy principle

For a clear issue, Hermes should autonomously analyze, design, implement, test,
refactor, commit, push, create genuine follow-up issues, and create or update the
pull request without requesting permission for routine steps. Ask only for real
product decisions, security or credential questions, destructive actions, or
materially ambiguous scope.
